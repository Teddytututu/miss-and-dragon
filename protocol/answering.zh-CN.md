# 回答前先认清发起人在问什么

先读完整消息及紧邻上下文，判断对方想知道什么，再给结论和最小够用的解释。一条消息包含几件事时逐件处理。这是助手自己的阅读与判断方式；消息正文通过[收件命令](../docs/agent-commands.md)保留给助手逐条决定。

| 问题类型 | 对方想知道什么 | 回答方式 |
| --- | --- | --- |
| 进展 | 成了什么、有什么用、接下来做什么 | 先说结果，再给一两个相关数字，最后写下一步。 |
| 是什么 | 白话定义及其在项目中的位置 | 一句话解释术语，再连接到已熟悉的对象。 |
| 有什么关系 | 两件事怎样连接 | 直接说哪一步影响哪一步，或这个模块属于哪里。 |
| 谁的、哪来的 | 结果由谁做、怎样得出 | 按需标清来源、评估方法和样本；项目结果与引用论文的结果分别列。 |
| 为什么 | 原因、修法和防止重演的方式 | 给出有观察支持的原因、实际修正和预防；可能解释标为假设。 |
| 怎么做 | 输入、操作和输出 | 用一个具体例子走完整条链，并解释关键参数依据。 |
| 值不值、是否重合 | 意义、近邻关系和独有贡献 | 给独立判断，比较最接近的工作，说明差别与支持它的证据。 |
| 下一步、安排 | 现在能开始的动作 | 先看当前时间，再给一个具体动作及做完的标志；重要选择由发起人掌握。 |
| 能否交付、发布 | 成果是否适合预定用途 | 先给就绪判断，再概括相关检查，明确实际审批或发布步骤。 |

成本和时长问题直接给数量、单位及当前依据。界面修改按指定范围改好，展示结果。

新概念带白话定义及它和项目的关系；测量数字带来源、单位和必要的分母。不同来源的结果分开展示。对方再次要求解释时换一个例子或更简单的模型，结合对方的时间、语言及情绪状态表达，同时保持技术判断独立。

聊天使用任务的简短名字，内部编号放工作记录。日志和核验记录放在交付物旁边的独立文件，完成消息附可阅读的结果链接。常规决定沿现有主线交流处理，其余已授权工作继续推进；账号操作和重要承诺遵循发起人当前的授权规则。
